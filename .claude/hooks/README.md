# Agent hooks

Claude Code hooks that turn `dou-ship` and `dou-verify` steps into checks. Why they exist and how a hook moves
from `observe` to `enforce`: [ADR-0369](../../docs/adr/0369-agent-gates-start-in-observe-and-escalate-to-a-person.md).

| Hook                     | Event                                                       | Would block                                                     |
| ------------------------ | ----------------------------------------------------------- | --------------------------------------------------------------- |
| `lint-edited-file.cjs`   | PostToolUse `Edit\|Write\|MultiEdit`                        | an edited source file with ESLint errors                        |
| `gate-before-commit.cjs` | PreToolUse `Bash`                                           | a `git commit` whose `yarn gate` fails; a missing `Verified-by:` trailer is its own check, `verified-by-trailer` |
| `check-escalation.cjs`   | PreToolUse, PostToolUse, PostToolUseFailure `Bash`; prompts | the same check failing a third time in a row                    |
| `verify-before-stop.cjs` | Stop                                                        | a turn that changed source and produced no verify report        |

Modes live in `modes.json`. Records go to `dou-hooks/` in the git common directory (shared by every worktree,
never committed); `DOU_HOOK_LOG_DIR` and `DOU_HOOK_MODES` point them elsewhere for tests.

## Which checkout runs them

The desktop app starts every session, worktrees included, with `--project-config-root` set to the main
checkout. Claude Code then reads `.claude/settings*.json` from the main checkout, runs hooks with that
directory as their working directory and as `CLAUDE_PROJECT_DIR`, and ignores the worktree's own settings.
The main checkout is often on a release branch that predates a hook, so a command naming
`$CLAUDE_PROJECT_DIR/.claude/hooks/…` either finds nothing or runs another branch's copy.

So each command in `.claude/settings.json` is a small dispatcher: it reads the session's `cwd` from the hook
input, runs `.claude/hooks/<name>.cjs` from that checkout with `CLAUDE_PROJECT_DIR` set to it, passes the exit
code through, and exits 0 when the checkout has no such hook. The commands are generated by
`scripts/install-claude-hooks.js`; a test fails when `settings.json` drifts from it.

`yarn hooks:install` copies the same `hooks` block into the main checkout's `.claude/settings.local.json`,
which no branch tracks, so the hooks stay on whichever branch the main checkout is on. It also holds each
developer's own permissions with home-directory paths, so `check:internal-paths` fails if it, `.claude/launch.json`
or a `.DS_Store` is ever tracked. Run it once per clone
and again after the hook list in `settings.json` changes. When the main checkout's branch also has
`settings.json`, Claude Code sees identical commands and runs each once.

The same root applies to `.claude/skills/` and `.claude/agents/`: desktop sessions see the main checkout's.
