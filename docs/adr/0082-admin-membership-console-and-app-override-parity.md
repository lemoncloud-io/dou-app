# ADR-0082: admin-v2에 관리자 구독 관리 화면을 두고, 앱의 구독 판정을 관리자 오버라이드에 맞춘다

> 상태: Accepted · 결정일: 2026-09-10

## 맥락 (Context)

운영자가 CS·정책 목적으로 유저 구독을 다룰 화면이 없다. 지금은 백엔드를 직접 호출하는 수밖에 없다.

### 백엔드는 이미 준비돼 있다

`chatic-backend-api`의 `feature/subscription-admin`이 develop에 머지됐고(`250ee59`) `v0.26.811a`로 배포됐다. 설계와 계약의 정본은 vault의 `projects/@lemoncloud-io/chatic-backend-api/specs/subscription-admin/`(README·high-levels·SPEC·plans)에 있다.

| 엔드포인트                                 | 하는 일                         | 상태                             |
| ------------------------------------------ | ------------------------------- | -------------------------------- |
| `GET {relay}/memberships/0/list`           | 관리자 멤버십 목록. 필터·페이지 | 사용 가능                        |
| `PUT {relay}/memberships/{userId}/admin`   | 관리자 오버라이드. `?auto=1`    | 사용 가능                        |
| `GET {relay}/clouds/0/list?view=admin`     | Cloud 목록 + 상태 집계          | 사용 가능                        |
| `POST {relay}/memberships/{userId}/cancel` | 스토어 연동 취소                | **없음** (Google 배선 대기, TBD) |

관리자 오버라이드는 영수증과 분리된 축 하나다. `adminStatus`(고정할 상태) · `adminUntil`(오버라이드 만료) · `adminProductId`(등급) 셋이 부여·차단·해제를 모두 표현한다. 축이 하나라 우선순위 규칙이 없다. 오버라이드는 저장된 값을 덮지 않고 파생 단계에서만 이긴다.

- **오버라이드 활성** = `adminStatus`가 있고, `adminUntil`이 없거나 `adminUntil > 현재`
- **부여** = `adminStatus: 'active'`, **차단** = `'expired'` 또는 `'canceled'`, **해제** = 빈 문자열
- **무기한** = 만료 시각을 두지 않는 것. 특수값(`-1`, 별도 플래그)을 쓰지 않는다
- 과거 시각과 음수는 서버가 거부한다

### 조사에서 나온 것 (2026-09-10 실측)

**1. 관리자 오버라이드가 앱 화면에는 반영되지 않는다.** `apps/web`의 `summarizeMembership`([membershipStatus.ts](../../apps/web/src/app/features/subscription/lib/membershipStatus.ts))은 서버의 `isValid`를 **의도적으로** 쓰지 않는다. 예약 취소가 남은 유료 기간을 0으로 만들기 때문이다. 대신 영수증의 `validUntil`과 `status`로 직접 판단한다. 그래서 오버라이드가 서버에서만 작동한다.

| 관리자 조작               | 서버              | 앱 화면                             |
| ------------------------- | ----------------- | ----------------------------------- |
| 기간 부여 (영수증은 만료) | 유효 · Cloud 복원 | "만료" — `validUntil`이 과거라서    |
| 차단 (영수증은 살아 있음) | 무효 · Cloud 보류 | "이용 중" — `validUntil`이 미래라서 |
| 등급 부여                 | 상한 늘어남       | 그대로 — 앱은 `productId`만 읽음    |

이 구멍은 백엔드 스펙에 적혀 있지 않다. 콘솔만 만들면 "서버는 바꿨는데 유저 화면은 안 바뀐" 상태가 만들어진다.

**2. 앱은 아직 `isSuper`를 읽는다.** 백엔드 스펙의 열린 질문 Q5는 "앱이 응답의 `isSuper`를 읽지 않는 것이 확인되면 필드를 걷는다"고 남겨 두었다. 확인해 보니 읽는다 — `membershipStatus.ts:60`에서 다른 판단보다 먼저 early return한다. 백엔드는 B0(2026-08-31)로 판정에서 이미 걷었으므로, 지금은 앱만 옛 축을 보고 있다.

**3. 스펙의 파라미터 이름이 틀렸다.** 문서는 유저별 Cloud 조회를 `?view=admin&userId=`로 적었다. 코드에서 `userId`는 `view=mine` 분기에서만 쓰인다(`chatic-backend-api`의 `src/modules/clouds/api-clouds.ts:220`). 관리자 조회로 유저를 거르려면 `ownerId`를 넘겨야 한다. 또 `valid` 기본값이 `1`이라 만료된 Cloud가 빠진다.

**4. `status`와 `isValid`가 어긋날 수 있다.** 목록의 `status`는 마지막 쓰기 때 파생해 저장한 값이고, `isValid`는 조회 시점에 다시 파생한다. 오버라이드 만료를 되돌리는 배치가 없어서(스펙 함정2), 부여 기간이 끝나도 재조회 전까지 `status='active'`인 채 `isValid=false`로 나온다.

### 제약

- **admin-v2는 어디에도 배포되지 않는다.** dev·prod 워크플로가 둘 다 강제로 건너뛴다 — `libs/socket → web-core` 때문에 `admin:build`가 깨져서다([deploy-dev.yml:12](../../.github/workflows/deploy-dev.yml)). 콘솔은 개발자 로컬에서 각자의 `.env`로 돌아간다. report-logs가 기본 `v1`(운영)을 읽는 것으로 보아, 로컬에서 운영 데이터를 보는 것이 지금의 운용 방식이다.
- 물려 있는 `@lemoncloud/chatic-backend-api`가 `0.26.810`이고 거기엔 오버라이드 필드가 없다. npm의 `0.26.811`에는 있다.
- 관리자 판정은 서버의 `hasAdminRole()`이고, 콘솔 진입은 `ProtectedRoute`의 `$role.role === 'admin'` 게이트가 이미 막고 있다.

## 결정 (Decision)

### 포함

**1. 화면 셋을 admin-v2에 만든다.** 멤버십 목록 · 관리자 오버라이드 · 유저별 Cloud 목록. 상단 내비에 항목을 하나 더한다.

**2. 배선은 공유 libs 3계층을 쓴다.** `libs/http`의 `subscriptions` 게이트웨이 → `libs/data`의 `SubscriptionHttpDataSource` → `SubscriptionRepositoryV2`를 확장하고, 앱은 `runtime.data.useRuntimeRepositories()`로 받는다. `users` 피처의 선례를 따른다. 구독 표면이 이미 그 세 계층에 있고, 리포지토리는 이미 런타임에 배선돼 있어 admin-v2에서 바로 쓸 수 있다.

**3. 타입은 패키지를 `0.26.811`로 올려서 얻는다.** `package.json`이 이미 `^0.26.810`이라 락파일만 갱신하면 된다. 810과 811의 차이는 필드 6개 추가와 `@deprecated` 주석뿐이고 깨지는 변경이 없다(두 tarball 실측).

**4. 유저 식별은 `userId`로만 한다.** 멤버십 응답에는 이름도 이메일도 없다. 목록은 `userId`·상태·상품·기간만 보여 주고, 특정 유저는 `userId` 필터로 찾는다. 행마다 유저 조회를 덧붙이지 않는다.

**5. 대상 서버는 표시만 한다.** 현재 backend 엔드포인트와 운영/개발 배지를 화면에 박아 둔다. 화면에서 스테이지를 바꾸지는 않는다 — 서버를 바꾸려면 `.env`를 고치고 다시 띄운다.

**6. 쓰기 조작에 안전장치 넷을 둔다.**

- 사유(`adminReason`) 입력을 콘솔에서 필수로 만든다. API는 선택이지만 콘솔이 강제한다.
- 실행 전 확인 다이얼로그에 무엇이 바뀌는지 문장으로 적는다. 차단은 Cloud를 멈추고 `auto`는 Cloud를 만든다.
- `auto`(즉시 Cloud 생성)는 기본 꺼짐. 명시적으로 켤 때만 보낸다.
- 대상 서버 배지를 쓰기 화면에서도 보이게 둔다.

**7. `apps/web`의 구독 판정을 오버라이드에 맞춘다.**

- `summarizeMembership`이 `adminStatus`·`adminUntil`·`adminProductId`를 읽는다. 서버와 같은 규칙으로 활성 여부를 파생한다.
- 차단을 위해 `SubscriptionState`에 `blocked`를 더한다. `expired`로 접지 않는다. 결제가 계속 나가는 상태를 "만료"라고 말하면 안 된다.
- 활성 오버라이드에 `adminProductId`가 있으면 그것을 유효 등급으로 쓴다.
- **`isSuper` 읽기를 걷어낸다.** 오버라이드만 읽는다. 이로써 백엔드의 Q5가 닫히고 필드를 지울 길이 열린다.

### 제외

- **구독 취소.** 백엔드에 엔드포인트가 없다. Apple은 스토어가 서버발 취소를 제공하지 않아 오버라이드 차단이 대신하고, Google 배선은 아직 안 됐다.
- **admin-v2 배포 복구.** `libs/socket → web-core`가 `admin:build`를 깨뜨리는 문제는 별건이다. 이 트랙은 로컬 실행을 전제로 한다.
- **화면에서의 스테이지 전환.**
- **`isSuper` 필드 물리 제거.** 백엔드 몫이다. 이 ADR은 앱이 읽기를 멈추게 해서 그 선행 조건만 만든다.
- **오버라이드 이력 로그.** 백엔드가 최근 1건만 멤버십에 남기고 나머지는 슬랙으로 보낸다. 콘솔은 그 최근 1건만 보여 준다.

### dev-2 스펙으로 넘길 실측값

- 유저별 Cloud: `GET {relay}/clouds/0/list?view=admin&ownerId={userId}&valid=0`. `userId`가 아니라 `ownerId`다. `valid=0`이라야 만료된 Cloud까지 보인다. 상태 집계는 `aggr`로 같이 온다.
- 목록에서 `status`와 `isValid`가 어긋날 수 있다. 화면은 둘을 함께 보여 주고, 어긋나면 그 사실이 보이게 한다.
- 무기한은 `adminUntil`을 비우는 것이다. 먼 미래 날짜를 넣지 않는다.
- 해제는 `adminStatus: ''`다. 서버가 `adminUntil`과 `adminProductId`를 함께 비운다.
- 목록은 ES 검색이라 쓰기 직후 재조회가 옛 값을 낼 수 있다. `PUT`의 응답이 갱신된 뷰이므로 그것으로 행을 갱신한다.

## 대안 (Alternatives)

**배선을 앱 로컬에 둔다** (`report-logs`의 `runtime.boot.webTransport.buildSignedRequest` 선례). 관리자 전용 표면이 공유 libs에 안 들어가서 모바일 번들이 커지지 않고, ADR-0070이 콘솔 전용 표면을 앱으로 내리자고 한 방향과도 맞는다. 버렸다 — 구독 표면이 이미 세 계층에 다 있는데 관리자 메서드만 다른 길로 가면 같은 도메인이 두 갈래가 된다.

**타입을 피처 안에 로컬로 선언한다** (`report-logs`의 `RawMockView` 선례). 의존성을 안 건드려서 다른 앱에 파급이 없다. 버렸다 — 여기서는 SDK 타입이 실제로 같은 서버의 계약이고, 버전 차이가 순수 추가라 위험이 없다.

**화면에서 스테이지를 전환한다.** 게이트웨이가 `exec.resolveEndpoint('relay')`로 설정값 하나에서 baseURL을 만든다. 호출마다 스테이지를 바꾸려면 base override를 게이트웨이·데이터소스·리포지토리 셋 다에 뚫어야 한다. 콘솔 전용 개념을 공유 계층 셋에 흘리는 대가가 편의보다 크다.

**차단을 `expired`로 접는다.** 새 상태가 없어 화면을 안 건드려도 된다. 버렸다 — 결제가 나가는 유저에게 "만료"를 보여 주면 그대로 CS가 된다.

**앱의 `isSuper` 읽기를 남긴다.** 이관이 누락된 레코드가 있어도 아무도 갑자기 만료되지 않는다. 버렸다 — 두 축을 공존시키면 백엔드가 필드를 영영 못 지운다. 누락 여부는 이 콘솔로 확인할 수 있다(아래).

**콘솔에만 "앱에는 이렇게 보임"을 나란히 표시한다.** 앱을 안 건드리고 운영자가 불일치를 알게 한다. 버렸다 — 불일치를 보이게 할 뿐 없애지 않는다.

## 결과 (Consequences)

**얻는 것**

- 운영자가 화면에서 구독을 조회하고 기간·상태·등급을 부여·차단·해제할 수 있다. 부여·차단의 결과가 Cloud에 어떻게 반영됐는지 같은 화면에서 확인한다.
- 서버 판정과 앱 화면이 같은 진실을 보게 된다. 부여하면 앱도 유효하다고 말하고, 차단하면 앱도 제한을 말한다.
- 백엔드가 `isSuper`를 지울 선행 조건이 채워진다.
- 누가·언제·왜 조작했는지가 사유 필수화로 빠짐없이 남는다.

**감수하는 것**

- 관리자 전용 메서드가 공유 libs에 들어가므로 모바일 앱 번들의 표면이 그만큼 넓어진다. 트리셰이킹이 걷어 주기를 기대하되, 이 도메인의 표면이 한자리에 모이는 것을 대가로 받는다.
- 서버를 바꾸려면 `.env`를 고치고 다시 띄워야 한다.
- 배포 레인이 하나 늘어난다. 콘솔은 로컬이라 즉시 쓰지만 `apps/web` 변경은 웹 배포를 타야 한다. **콘솔이 먼저 살아나고 앱 반영은 뒤에 온다** — 그 사이의 조작은 서버에만 반영된다.
- `blocked` 상태의 문구를 새로 정해야 한다. 소비자는 `usePlanCatalog`와 `SubscriptionPage` 둘이라 파급은 작다.
- 콘솔은 배포되지 않으므로 사용자는 리포를 클론해 로컬에서 띄우는 사람으로 한정된다.

**검증할 것**

- `isSuper` 읽기를 걷기 전에, **이 콘솔로** `isSuper=1`인 멤버십을 걸러 전부 활성 오버라이드를 갖고 있는지 확인한다. `isSuper`는 문서화된 필터 필드다. 백엔드 로그는 7건 전부 이관하고 건너뜀 0이라고 적었지만, 앱에서 읽기를 걷는 변경의 근거로는 실측이 필요하다. 서버가 `isSuper`를 더 받지 않으므로 새로 생기지는 않는다.
- 관리자가 아닌 세션으로 목록 두 경로를 불러 403이 나는지 확인한다.
- 부여 → 앱에서 유효로 보이는지, 차단 → 앱에서 제한으로 보이는지, 해제 → 원래대로 돌아오는지를 한 유저로 이어서 확인한다.
- `0.26.811` 반영 후 `apps/web`·`apps/admin-v2`·`libs`의 타입체크가 기준선(web·admin-v2 0건)을 유지하는지 확인한다.

**남은 미결**

- 구독 취소는 Google 배선이 정해질 때까지 열려 있다. `cancel`(자동갱신만 끔)과 `revoke`(즉시 회수) 중 무엇이 요구인지도 아직 정해지지 않았다.
- 오버라이드 만료를 되돌리는 방아쇠가 서버에 없다. 유저가 앱을 열기 전까지 상한이 줄지 않는다. 백엔드 수명주기 T12 몫이다.
