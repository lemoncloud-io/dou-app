# ADR-0154: The launch splash is the only logo screen, and the web lifts it

> Status: Accepted · Decided: 2026-10-01
> · Scope: `libs/app-messages/src/types/model/system.ts` (`FirstScreenReady`, `holdsBootSplash`) ·
> `apps/web/index.html` · `apps/web/src/app/runtime/bootSplash.ts` ·
> `apps/mobile/src/app/services/bootSplash/` · `apps/mobile/android/.../MainActivity.kt` ·
> `apps/mobile/ios/Bridges/BootSplashOverlay.swift`
> · Partly supersedes [ADR-0054](./0054-theme-light-default-and-web-native-sync.md) (§5 `--splash-bg`,
> the dark-splash-asset and native-early-theme non-goals)
> · The module docs are [apps/mobile boot-splash](../../apps/mobile/docs/boot/boot-splash.md) and
> [apps/web boot-cover](../../apps/web/docs/shell/boot-cover.md)

## Context

A cold start in the app showed the same logo screen twice. Four layers drew a "loading" screen in
turn — the OS launch screen (plain white, no logo), an RN overlay with the logo, the web's `#splash`
inside `#root` with the logo, and the web's `LoadingFallback` with the logo and dots — and between
them sat frames where nothing drew the logo at all: the session gate and the router both render
`null` while they wait. The overlay also came down on `WebAppReady`, which the web sends before React
renders, or on a 1s timer, so it could lift onto a WebView that had not painted. And the four logos
did not match: `#splash` stretched the 1115×983 logo into a 96×96 box, `LoadingFallback` sat 13px
higher because its dots shared the centring.

## Decision

**The native launch splash is the only thing that draws the logo, and it is held until the web has
painted its first real screen.** Every other cover is the theme background.

- **Native holds.** Android keeps the SplashScreen API splash with `setKeepOnScreenCondition`,
  re-armed in every `onCreate` (a warm start recreates the Activity while JS lives on); iOS lays a
  copy of the launch storyboard over the window once RN starts, because the OS drops its own as soon
  as the app draws.
- **The web releases.** Only the web knows when a screen is up. `index.html` paints a background-only
  cover outside `#root`; `runtime/bootSplash` removes it two animation frames after the router mounts
  its first route with no hold left (a lazy route loading, a cold-start deep link not yet applied, a
  signed-out root still waiting for its session), then posts the new fire-and-forget `FirstScreenReady`,
  on which native lifts its splash — a 200ms fade on iOS; on Android the system's own exit, since
  a custom exit animation makes the system hand its splash to the app, and on a busy start that
  handover times out and shows the splash twice.
- **Version skew is declared, not guessed.** The web says it will send the signal with
  `WebAppReady.holdsBootSplash: true`. A shell that sees no flag lifts its splash on the handshake —
  an older web never sends `FirstScreenReady`. An older shell answers the post `NOT_FOUND`, which
  nothing waits on.
- **Every exit is capped.** Native lifts itself 5s after showing, the web its cover after 10s; a page
  load error, the deep-link error view, and the error boundaries reveal at once.
- **Nothing raises an OS prompt under the splash.** The notification permission request waits for
  the reveal (or the 5s cap). On Android, a permission activity opened over the held splash played
  its transition onto the app's undrawn window — black for over a second, then the splash again.
- **The splash takes the app theme where the platform lets it.** The in-app theme is handed to native
  on every start and change (`setStartupTheme`): Android 12+ through `setApplicationNightMode`, which
  the system applies to the next launch's splash; iOS by overriding the overlay view's style. The very
  first frame on iOS and Android ≤ 11 is the OS launch screen, drawn before any app code, and stays
  in the OS theme.

## Consequences

- One splash, then the screen, on cold and warm starts. Covers that are not a launch — the iOS resume
  overlay, the crash-reload cover, `LoadingFallback` — no longer flash a logo.
- A slow boot now sits on a static logo for up to 5s with no progress cue; after that the web cover's
  dots take over. That trade was made deliberately for the common fast boot.
- An OS-light, app-dark user on iOS or Android ≤ 11 still sees one colour change, at the first
  app-drawn frame (faded over 200ms on iOS). Every iOS app with an in-app theme has the same first
  frame.
- `setApplicationNightMode` changes the Android app's configuration. That is safe only because
  `android:configChanges` includes `uiMode` and `'system'` maps to `MODE_NIGHT_AUTO`; dropping either
  would recreate the Activity or skew `useColorScheme`.
- The splash PNGs are generated from `assets/src/logo/logo.png` and must be regenerated by hand when
  the logo changes. The iOS simulator caches launch screens, so a storyboard change needs an erased
  simulator to be seen.
- A screen that renders its own skeleton while its data loads counts as painted: the cover waits for
  the route, not for the route's data.

## Alternatives

- **Keep all four layers and make them pixel-identical.** Every layer would have to agree on asset,
  size, centre and colour across three rendering engines, and the `null` gates would still blink.
  Rejected: the flicker comes from layers handing over, so the fix is fewer handovers.
- **Native splash until `WebAppReady`.** Simple and needs no new message, but `WebAppReady` is sent
  before React renders, so it hands over to a blank page — the original bug, one layer down.
- **A fixed delay after load.** The old 300ms deep-link hold and 1s fallback did this; any number is
  either too short on a slow device or a wasted wait on a fast one.
- **A logo in the web cover as a safety net.** It would only ever be seen as a second, slightly
  different copy whenever the native splash had already gone (cap, reload, browser). The background
  alone is what those cases need.
- **`react-native-bootsplash`.** It solves the iOS hold the same way, but adds a dependency and pods
  for two calls per platform; the Android side already had `core-splashscreen`.
