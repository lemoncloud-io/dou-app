# ADR-0075: 클라우드 활성 알림을 앱에서 받을 준비를 한다

> 상태: Accepted · 결정일: 2026-09-07

## 맥락 (Context)

서버(`chatic-backend-api`)가 클라우드 자원 확보 축이 `reserved` → `active`로 올라가는 순간
소유자에게 알림 한 건을 던지는 작업을 착수한다 (그쪽 스펙: `specs/cloud-ready-push`).
전달은 `chatic-sockets-api`의 단건 전달에 맡기고, **접속 중이면 웹소켓, 아니면 푸시**로 갈린다.

| 경로   | 봉투                                              | 내용                                                                                                                                                         |
| ------ | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 푸시   | —                                                 | `type: 'cloud'` · `title_loc_key: 'push_cloud_activate_title'` · `title_loc_args: [name \|\| id]` · `data: { cid, uid }`. `loc_key`·`link`·`channel_id` 없음 |
| 웹소켓 | `type: 'cloud.activated'` · `subject: cloud:<id>` | `data: { id, name }`                                                                                                                                         |

규격 정본은 vault의 `dou-app/push-payload`이고 앱팀이 확정한 것이다. 서버는 이 규격을 바꾸지
않는다. 그런데 **앱이 그 확정본을 아직 받아들이지 않은 상태**여서, 서버가 먼저 배포되면 알림이
깨지거나 오작동한다. 코드를 조사해 확인한 갭은 다음과 같다.

1. **번역 키가 어디에도 없다.** `push_cloud_activate_title`이 다섯 자리 전부에 비어 있다 —
   `libs/i18n-mobile/src/locales/{ko,en}.ts`, `apps/mobile/android/app/src/main/assets/locales/{ko,en}.json`,
   `apps/mobile/ios/assets/locales/{ko,en}.json`, `apps/mobile/ios/ChaticNotificationServiceExtension/{ko,en}.json`.
   Android FCM 서비스와 iOS Notification Service Extension은 키를 못 찾으면 키 문자열을 그대로
   배너에 쓰므로, 잠금화면에 리터럴 `push_cloud_activate_title`이 뜬다.
2. **죽은 키가 그 자리를 이미 차지하고 있다.** `notification.cloud.sync_complete`
   ("클라우드 '{0}' 생성 완료")가 같은 다섯 자리에 있는데 참조하는 코드가 0건이다. 정본 문서도
   중첩 `notification.*` 키는 명명 규칙 이전의 잔재라고 못박았다.
3. **포그라운드에서 오탐이 난다.** `CloudPushMarkRunner`가 푸시의 `type`을 보지 않고 `cid`만
   보고 크로스 클라우드 안 읽음 점을 켠다 (ADR-0056). 클라우드 활성 푸시는 새 클라우드의 `cid`를
   싣고 오므로, **방금 만들어진 클라우드에 "안 읽은 메시지" 점이 켜진다.** 백그라운드 경로는
   이미 막혀 있다 — Android는 `isChatChannel(channelId)` 게이트, iOS는 `appendPushMarkIfNeeded`가
   `applyBadgeIncrementIfNeeded`의 chat 게이트 안쪽에 있다. 포그라운드 브릿지만 뚫려 있다.
4. **탭에 목적지가 없다.** `link`가 비어서 `resolvePushTapPath`가 `null`을 돌려주고, 탭은 앱을
   포그라운드로 올리기만 한다. 정본 문서는 "`link`가 비면 루트"라고 적었지만 코드는 루트로 가지
   않는다 — 문서와 코드가 어긋난 지점이다.
5. **웹소켓 이벤트를 아무도 듣지 않는다.** `cloud.activated` 구독처가 앱·웹 어디에도 없다.
   서버 스펙은 "앱이 그 유형을 모르면 웹소켓 전달은 버려지고 푸시만 남는다"고 적었으나, 실제로는
   접속 중일 때 전달 계층이 **푸시를 건너뛴다.** 즉 앱을 켜 둔 사용자는 아무것도 받지 못한다.

제약 셋이 이 결정을 좁힌다.

- **C1.** 문구·페이로드·채널 규격은 정본 문서가 소유한다. 앱은 그 규격을 받아들이기만 한다.
- **C2. 앱 배포가 서버 발송보다 먼저다.** 번역 키가 없는 구버전 앱은 리터럴 키를 보게 된다.
- **C3.** 웹 i18n은 원격 리소스(`i18next-xhr-backend`)에서 받는다. 인앱 배너 문구는 이 리포 밖
  i18n 서버에 먼저 올라가야 한다. 네이티브 셸 로케일(`libs/i18n-mobile`, 네이티브 assets)과는
  다른 계통이다.

## 결정 (Decision)

앱을 서버 발송보다 먼저 "받을 수 있는 상태"로 만든다. 네 가지를 한다.

### 1. 번역 키 정착과 죽은 키 제거

`push_cloud_activate_title`을 위 다섯 자리 전부에 넣는다. 문구는 정본 확정본 그대로다 —
한국어 `{0} 클라우드가 준비되었습니다`, 영어 `{0} is ready`. 같은 변경에서 참조가 0건인
`notification.cloud.sync_complete`를 다섯 자리에서 지운다.

**하나라도 빠지면 그 경로에서만 문구가 깨진다.** 다섯 자리는 서로 다른 소비자다 — 네이티브 셸
UI, 타입 도달성, Android 푸시 조립, iOS 앱, iOS 푸시 조립. iOS Extension 로케일 파일은
Extension 타깃의 Copy Bundle Resources에도 들어 있어야 한다.

### 2. 포그라운드 오탐 게이트

`CloudPushMarkRunner`의 포그라운드 핸들러가 채팅 푸시일 때만 점을 켜도록 막는다. 판정 재료는
이미 웹에 도착해 있다 — `useFcmHandler`가 Android 포그라운드 이벤트의 `type`을 `data.type`으로
실어 보내고, iOS는 APNs `userInfo`의 최상위 `type`이 그대로 넘어온다.

**게이트는 "채팅만 통과"이지 "클라우드만 차단"이 아니다.** 앞으로 늘어날 알림 유형이 자동으로
막히는 쪽이 맞다 — 유형이 늘 때마다 차단 목록을 늘리는 것은 잊기 쉽다.

백그라운드 경로는 손대지 않는다. 이미 `isChatChannel` 게이트 안쪽이라 같은 규칙이 서 있다.

### 3. 탭은 홈으로

푸시 탭 목적지를 홈(`/`)으로 정한다. 정본 문서의 "`link`가 비면 루트"를 코드가 실제로 지키게
만드는 것이다. 해당 클라우드로 전환하지 않는다 — 기획이 이동을 홈으로 확정했고, 클라우드 전환은
앱의 다른 규칙(세션 핸드셰이크·컨텍스트 전환)에 걸린다.

### 4. `cloud.activated`를 relay 슬롯에 고정 구독

`SocketManager`에 **슬롯을 지정하는 구독**을 더하고, `cloud.activated`를 relay 슬롯에 묶는다.
받으면 두 가지를 한다 — **클라우드 목록 캐시 무효화**(`cloudsKeys.all`)와 **인앱 배너**.

**relay 고정이 핵심이다.** 지금의 `SocketManager.onType()`은 active 슬롯에만 바인딩하고,
active는 "cloud가 있으면 cloud, 없으면 relay"다. 그런데 이 unicast는 `targetType: 'user'`로
**중계서버 배포**에서 나간다. 그래서 active 구독을 쓰면 **사용자가 클라우드 안에 있을 때 놓친다**
— 두 번째·세 번째 클라우드를 추가하는 전형적인 상황이 정확히 그것이다. 슬롯 두 개는 동시에
붙어 있으므로(`entries: Map<SocketKind, ClientEntry>`) relay 클라이언트는 그때도 살아 있다.

새 구독은 기존 `onType`과 같은 소유권 규칙을 따른다 — 매니저가 엔트리를 소유하고, 슬롯이
재바인드될 때 다시 붙인다. active 전환에 반응하지 않는 대신 **relay 슬롯의 재바인드**에 반응한다.

배너는 클릭해도 클라우드로 전환하지 않는다. 푸시 탭(결정 3)과 목적지를 어긋나게 두지 않는다.

### 범위

**포함:** 위 넷.
**제외:**

- 서버 발신부·전달·푸시 전송 (`chatic-backend-api`·`chatic-sockets-api`·`chatic-pushes-api`)
- 재시도와 데드레터 — 전달 경로 어디에도 없다
- 복귀·설정 실패·삭제 완료·초과 비활성 알림 — 기획 미결
- 클라우드 알림의 배지·안 읽음 반영 — 대화 채널 전용이라는 기존 결정을 유지한다
- 인앱 배너 카드의 유형별 레이아웃 분기 (아래 대안 참고)

## 대안 (Alternatives)

- **웹소켓 이벤트를 무시하고 푸시만 준비** — 전달 계층이 접속 중이면 푸시를 건너뛰므로, 앱을
  켜 둔 사용자가 아무것도 받지 못한다. 원래 풀려던 문제(닫아 둔 사용자)는 풀리지만 켜 둔
  사용자의 체감이 지금보다 나빠질 여지가 없다는 전제가 틀렸다. 기각.
- **지금의 active `onType`을 그대로 사용** — 코드가 짧지만 클라우드 안에서 다음 클라우드를
  추가하는, 가장 흔한 경우를 놓친다. 기각.
- **서버가 중계서버와 활성 클라우드 양쪽에 unicast** — 앱 변경은 적지만 다른 레포에 의존이
  생기고, 같은 알림이 두 번 도착하는 중복 억제를 새로 만들어야 한다. 기각.
- **탭 시 해당 클라우드로 전환** — `data.cid`가 있으니 기술적으로 가능하다. 그러나 기획이
  이동을 홈으로 확정했고, 정본 문서의 문구도 그 전제("눌러도 그 클라우드로 전환되지 않으므로
  어느 클라우드인지 제목이 알려야 한다") 위에서 정해졌다. 기각.
- **인앱 배너에 유형별 분기 신설** — 정본 문서가 선행 과제로 적어 둔 항목이다. 그러나 코드를
  확인한 결과 `useInAppPushMessage`의 억제 규칙 둘(`ownerId` 자기 에코, 현재 방)은 클라우드
  푸시에서 조용히 no-op이 되고, 제목만 있는 클릭 없는 카드로 무해하게 뜬다. 깨지지 않는 것을
  지금 가르지 않는다. 기각 — 문서 쪽이 낡았다.
- **`notification.cloud.sync_complete`를 재사용** — 이미 다섯 자리에 있고 뜻도 비슷하다.
  그러나 정본이 확정한 키 이름·문구와 다르고("생성 완료" vs "준비되었습니다"), 중첩 키는 명명
  규칙 이전의 잔재다. 서버는 확정된 키만 보낸다. 기각.

## 결과 (Consequences)

**얻는 것**

- 서버가 배포되는 즉시 알림이 정상 문구로 닿는다. 앱 쪽이 병목이 아니게 된다.
- 접속 중·접속 끊김 양쪽 모두 커버된다 — 웹소켓과 푸시가 서로의 빈자리를 메운다.
- 새 클라우드에 가짜 안 읽음 점이 켜지는 오탐이 사라지고, 앞으로 늘어날 알림 유형도 같은
  게이트에 자동으로 막힌다.
- 죽은 키 다섯 벌이 사라진다.

**트레이드오프**

- **`SocketManager`의 공용 API가 늘어난다.** 슬롯 지정 구독은 active 구독과 재바인드 규칙이
  달라, 두 가지 구독 방식이 공존하게 된다. 어느 쪽을 써야 하는지가 호출부의 판단이 된다.
- **배포 순서가 제약이 된다.** 앱 스토어 심사를 거쳐 이 빌드가 퍼지기 전에 서버가 발송을 켜면
  구버전 사용자는 리터럴 키를 본다. 서버팀과 순서를 맞춰야 한다. 웹이 앱보다 먼저 배포되는
  이 리포의 관례와 방향이 반대다.
- **인앱 배너 문구는 리포 밖에 의존한다.** 웹 i18n은 원격 리소스라 이 리포의 변경만으로는
  배너 문구가 나오지 않는다 (C3).
- **웹소켓 봉투 유형이 서버 소유로 남는다.** `cloud.activated`라는 문자열을 앱이 하드코딩해
  구독하므로, 서버가 유형 이름을 바꾸면 조용히 끊긴다. 계약이 타입으로 강제되지 않는다.
- **중계서버 배포에 클라우드 식별자가 설정되면 푸시가 통째로 거부된다.** 서버 쪽 미결 항목이며
  앱이 막을 수 없다. 그때는 웹소켓 경로만 남는다.
