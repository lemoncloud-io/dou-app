# ADR-0083: admin-v2 로그 모니터링 화면을 추적 콘솔로 재편

> 상태: Accepted · 결정일: 2026-09-10

## 맥락 (Context)

`apps/admin-v2`의 Report Logs 화면(`features/report-logs`)은 `GET /dou-{stage}/mocks/0/list`로
제보(issue) · 배치 업로드 로그(log-entry) · 폐지된 자동 에러 리포트를 한 목록에서 읽는다.
운영에서 쓰려니 세 가지가 걸렸다.

**1. 필터가 페이지 단위다.** 검색어와 App 필터가 클라이언트에서 **현재 페이지 100건 안에서만**
돈다. 전체가 7.7k건이라 특정 유저의 로그를 찾는 건 사실상 불가능하다.

**2. 서버가 걸 수 있는 축이 정해져 있다.** `doGetList`는 쿼리 파라미터를
`MockTransformer.bodyToModel` → `packSearchParam`으로 걸러 `MockModel` 필드에 대한 ES term
필터로 바꾼다. `saveLogEntry`가 문서 최상단에 올려두는 조회 축 사본이 전부다.

| 구분           | 축                                                                                                  |
| -------------- | --------------------------------------------------------------------------------------------------- |
| 서버 필터 가능 | `uid`, `sid`, `cid`, `runId`, `level`, `type`(stereo), `from`/`to`, `sort`, `limit`/`page`/`offset` |
| 서버 필터 불가 | `tag`, `route`, `appVersion`, `webVersion`, `os`, `source`, `message` 본문                          |

불가 축은 `meta` JSON 문자열 안에만 있고 hoist 사본이 없다. 전문검색 경로도 없다.
그리고 `aggr`은 `buildQuery`에서 `aggregation: 'stereo'`로 고정돼 있어 서버 집계를 쓸 수 없다.

**3. 시각이 두 개다.** `LogEntry.timestamp`(발생)와 `createdAt`(서버 도달)이 다르다.
배치 업로드라 도달이 뭉쳐 들어오는데, 서버 필터·정렬은 `createdAt`만 된다.
지금 `bucketReportLogs`가 `createdAt`을 쓰고 있어 추이 그래프가 실제 발생 분포가 아니다.

**제약**: 이번 작업은 `apps/admin-v2` 프론트 전용이다. `chatic-backend-api`는 건드리지 않는다.

**목표 시나리오** (네 개 모두 대상):

1. 특정 유저 장애 추적 — uid로 좁혀 그 사람의 로그를 시간순으로 재구성
2. 전체 에러 모니터링 — 지금 뭐가 터지고 있는지 감시
3. 제보(issue) 대응 — 제보를 받아 그 사용자의 그 시점 로그와 대조
4. 릴리스 회귀 확인 — 버전별 에러 분포 비교

## 결정 (Decision)

Report Logs를 **한 화면 3분할 추적 콘솔**로 재편한다.

### 1. 화면 구조 — 3분할 + 추적 핀

- **좌**: 필터 레일
- **중**: 목록 / 집계 / 추이 전환
- **우**: 상세 **고정 패널** — 현재 오버레이 `ReportDetailDrawer`를 폐기한다.
  추적은 목록과 상세를 동시에 봐야 하는 작업이라 왕복이 비용이다.
- **상단**: 요약 모니터링 스트립(레벨별 카운트·급증) + **추적 핀 칩**

**추적 핀**: 행이나 상세에서 `uid` / `cid` / `runId`를 클릭하면 상단에 컨텍스트 칩으로
고정되고 **서버 필터로 승격**된다. 이것이 시나리오 1·3을 성립시키는 장치다.
`runId`는 앱 실행 한 구간이므로, runId 핀은 그 실행의 시간순 타임라인을 연다.

화면을 모니터링 대시보드와 추적 탐색기로 쪼개지 않는다. 제보 → 유저 → 로그로 넘어가는
이동이 한 화면에서 끊기지 않아야 한다.

필터·핀 상태는 URL 쿼리스트링에 반영한다(링크로 공유). socket-lab의
`?observe=<uid>` 연계는 유지한다.

### 2. 토대 데이터 — 기간 선축소 + 자동 연속 페치

서버가 태그·버전을 못 거르므로, 클라이언트가 볼 모집단을 넉넉히 확보한다.

1. 기간 · 레벨 · 타입 · 핀으로 **서버에서 먼저 좁힌다**
2. 그 결과를 `limit=100`씩 **연속으로 받아 누적한다** (상한 5,000건, 진행률 표시)
3. 태그 · 버전 · 라우트 · 메시지 필터와 집계는 **누적된 모집단 전체** 위에서 돈다
4. 상한에 닿으면 "기간을 좁히라"고 유도한다 — 조용히 자르지 않는다

`limit=-1`(noLimit)과 큰 단일 `limit`은 쓰지 않는다. 제보 레코드의 `meta`에 스크린샷
base64가 들어 있어 단일 응답이 터진다.

### 3. 실시간성 — 새 로그 배너

누적된 모집단은 자동으로 갱신하지 않는다. 백그라운드로 1페이지만 짧게 찍어보고
새 것이 있으면 상단에 `새 로그 N건 · 받기` 배너만 띄운다. 누르면 머리에 붙인다.
분석 중에 화면이 발밑에서 뒤집히지 않는다.

### 4. 시간 기준 — 발생 시각 우선

- 서버 조회 · 기간 필터: `createdAt` (선택지가 없다)
- 화면 정렬 · 타임라인 · 추이 그래프: `timestamp` 우선, 없으면 `createdAt` 폴백
- 두 값이 크게 벌어진 행에는 지연 배지를 붙인다
- 기간 가장자리의 샘(어제 발생 · 오늘 도달)은 화면에 명시한다

### 5. 외형 — ui-kit으로 통일

`@chatic/ui-kit`(memberships 화면이 이미 쓰는 shadcn 계열)으로 통일한다.
지금 report-logs는 tailwind 인라인 생짜다.

### 범위에서 제외

- `chatic-backend-api` 수정 일체 — 조회 축 추가(`tag`/`route`/`appVersion` hoist),
  `aggregation` 파라미터화, 전문검색 경로
- 서버 집계(`aggr`) 활용 — `stereo` 고정이라 쓸 데가 없다
- 로그 보존·삭제·알림(슬랙 등) 기능

## 대안 (Alternatives)

**백엔드도 같이 수정** — `tag`/`appVersion`을 최상단으로 hoist하고 `aggregation`을
파라미터화하면 시나리오 2·4가 정확해진다. 버렸다: 이번 범위는 프론트 전용이고,
hoist는 기존 레코드에 소급 적용되지 않아 재색인 문제가 따라온다. 다만 이 화면을 쓰다
보면 결국 필요해질 항목이라 위에 명시해 남긴다.

**현재 표본(최근 1,000건) 유지** — 구현이 가볍다. 버렸다: 시나리오 2·4가 계속 "느낌"에
그친다. 태그별 급증도 버전별 분포도 최근 1,000건이 대표성이 없다.

**큰 limit 한 방(2,000~5,000)** — 연속 페치 로직이 없어 짧다. 버렸다: 제보 스크린샷
base64가 섞이면 단일 응답이 수백MB가 될 수 있어 화면이 멈춘다.

**화면 2개로 분리(대시보드 / 추적 탐색기)** — 각자 단순해진다. 버렸다: 대시보드에서
뭔가 보이면 화면을 건너가며 문맥을 잃는다. 시나리오 3이 특히 끊긴다.

**자동 갱신 상시(15초 폴링)** — 항상 최신이다. 버렸다: 누적 모집단을 매번 다시 긁어
스크롤·선택이 퍼지고 네트워크가 방해된다.

**시각을 `createdAt`으로 통일** — 서버와 어긋나지 않고 기간 경계가 정확하다.
버렸다: 한 배치로 올라온 로그들이 거의 같은 시각이 되어 사건의 순서를 모른다.
추적의 핵심이 순서인데 그걸 잃는다.

## 결과 (Consequences)

**얻는 것**

- uid / cid / runId 추적이 전체 데이터에 대해 성립한다 — 페이지 안 검색이 아니다
- 태그 · 버전 집계가 "그 기간 전수" 기준이 된다 (상한 내)
- 실제 사건 순서가 화면에 나온다
- 목록 ↔ 상세 왕복이 사라진다
- 필터 상태가 링크로 공유된다

**감수하는 것**

- 연속 페치는 첫 화면 이후로 시간이 걸린다. 진행률과 상한 유도로 정직하게 드러낸다
- 5,000건 상한 밖은 안 보인다. 기간을 좁히는 게 해법이며 화면이 그렇게 말한다
- 기간 가장자리에서 발생/도달 기준 차이로 샘이 생긴다 — 없앨 수 없어 표기한다
- 태그 · 버전 필터는 여전히 클라이언트다. 백엔드 hoist 없이는 이게 천장이다
- `ReportDetailDrawer` 폐기로 `ReportDetailDrawer.spec.tsx`(210줄)를 새 상세 패널에 맞춰
  다시 써야 한다
- 배너 방식은 "완전 실시간"이 아니다. 새 로그를 받는 데 클릭 한 번이 든다
