# [아키텍처 표준] 전역 모듈 서비스 클래스 마이그레이션 명세서

## 1. 마이그레이션 목적

기존 객체 리터럴(Object Literal) 방식의 모듈들을 **Interface + Class 기반의 의존성 주입(DI) 구조**로 전환합니다.

- **확장성 & 테스트 용이성:** 인터페이스를 통한 명확한 입출력 정의 및 Mocking(테스트) 지원.
- **백그라운드 안정성:** React 생명주기(Lifecycle)와 독립적으로 실행되어야 하는 Headless JS 환경(FCM 백그라운드 등)에서의 안정성 확보.
- **결합도 최소화:** 모듈 간 참조를 의존성 주입(DI)으로 해결하여 스파게티 코드를 방지.

---

## 2. 계층형 설계 표준 (Design Standards)

모든 전역 서비스는 다음 4단계 계층을 엄격하게 분리하여 구현해야 합니다.

### Phase 1: Interface (명세 계층)

- 모듈이 외부에 제공할 퍼블릭 API(메서드, 반환 타입)를 반드시 `interface`로 가장 먼저 정의합니다.
- 클래스 구현체에 종속되는 내부 로직이나 변수는 인터페이스에 포함하지 않습니다.
- **네이밍 규칙:** `I` Prefix 사용 (예: `I[ServiceName]Service`)

### Phase 2: Class (구현 계층)

- Phase 1에서 정의한 인터페이스를 `implements` 하여 작성합니다.
- 모듈의 내부 상태(캐시, 플래그 등)는 반드시 `private` 또는 `protected`로 캡슐화합니다.
- **외부 모듈 호출 금지:** 클래스 내부에서 다른 전역 서비스(예: 로깅, DB)를 직접 `import`하여 호출하지 마십시오. 필요한 의존성은 **반드시 생성자(Constructor)를 통해 주입(Injection)** 받아야 합니다.

### Phase 3: Dependency Injection (주입 계층)

- 앱이 구동되는 최상단(또는 DI 전용 설정 파일)에서 각 클래스의 인스턴스를 단 한 번만 생성(Singleton)합니다.
- 클래스 간의 의존성(예: A 모듈이 B 모듈을 필요로 함)은 이 인스턴스화 단계에서 조립됩니다.
- 개별 작업자는 이 주입 컨테이너에 본인이 구현한 클래스를 등록하는 것까지 완료해야 합니다.

### Phase 4: UI Adapter (React 연동 계층)

- React 컴포넌트(화면)에서는 클래스의 인스턴스를 직접 참조하거나 메서드를 호출하는 것을 지양합니다.
- UI 렌더링(상태 변화 감지)이 필요한 경우, 주입된 인스턴스를 내부적으로 호출하고 상태(State)를 반환하는 **Custom Hook**을 작성하여 제공해야 합니다.

## 3. 의존성 주입 (DI) 규칙 및 가이드

모듈 간의 결합도를 낮추기 위해 **생성자 주입(Constructor Injection)** 방식을 기본 표준으로 채택합니다.

** [원칙 1] 단방향 의존성 주입**

- 코어 유틸리티(예: 로깅, 저장소)를 먼저 인스턴스화하고, 이를 필요로 하는 상위 서비스 모듈의 생성자에 인자로 넘겨줍니다.

** [원칙 2] 인터페이스 의존**

- 생성자에서 의존성을 주입받을 때는 특정 클래스 구현체가 아닌 **인터페이스 타입**으로 받아야 합니다. 이를 통해 추후 플랫폼별 구현체를 갈아끼우거나 테스트 런타임에서 Mock 객체로 대체할 수 있습니다.
- 인터페이스 및 서비스에 필요한 모델은 폴더 마다 개별의 `types.ts` 를 만들어 저장합니다.

** [원칙 3] 중앙화된 초기화 (DI Container)**

- 클래스 내부에서 `new` 키워드 사용을 엄격히 금지합니다.
- 모든 인스턴스의 생성 및 조립은 별도의 `provider.ts` (또는 지정된 초기화 파일)에서 일괄 수행하며, 앱 진입점(`index.js` 또는 `App.tsx`)에서 가장 먼저 로드되어야 합니다.

## 3. 작업 범위

최우선 타겟 모듈은 `apps/mobile/src/app/common/services/*`가 우선적인 타겟이 될 것이며, 개선된 모듈들은 `apps/mobile/src/app/services` 와 `apps/mobile/src/app/hooks`에 포함됩니다.
그외 작업 대상들은 이번스코프에서 후속작업으로 이루어지니, 제외합니다.

---

## 4. 작업자 마이그레이션 프로세스

이 명세서에 따라 작업을 진행할 프론트엔드 개발자는 다음 순서를 준수해야 합니다.

1. **스펙 정의:** 할당받은 모듈의 기존 함수들을 분석하여 `Interface` 스펙을 도출합니다.
2. **클래스 캡슐화:** 기존 로직을 `Class` 내부에 이관하고, 외부 참조가 필요한 부분은 생성자 주입 형태로 변경합니다.
3. **DI 등록:** 지정된 의존성 주입 설정 파일에 구현한 클래스의 인스턴스 생성 로직을 추가합니다.
4. **Adapter 작성 (선택):** UI에서 해당 모듈을 사용 중인 경우, 기존 로직이 깨지지 않도록 Custom Hook 래퍼(Wrapper)를 구성합니다.

_(※ 대상 모듈별 구체적인 할당, 디렉터리 분리 구조 및 파일 네이밍 컨벤션은 디렉터가 별도의 작업 티켓을 통해 개별 지정할 예정입니다.)_
